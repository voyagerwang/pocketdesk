# 翻腕发送：免手动证书接入规划

状态：阶段 2（主方案实施）与阶段 3（Mac 控制台 HTTPS 配对码）已于 2026-09-11 落地；阶段 1（真机基线）、阶段 4（发布验收）仍需真实手机与现有网络环境，未完成时本文不构成"已支持"的宣称。Tailscale 路径已于同日经用户决策否决（见 §3 方案 B 与 §5）。

## 1. 目标与决策

手机端不得为翻腕发送下载、安装或手动信任 CA；安卓与 iPhone 同样适用。不得用安装 VPN、注册新账号、改浏览器实验设置来替代证书门槛。允许功能首次开启时必要的系统权限确认。

推荐分两层推进：默认网页按实际能力提供翻腕，无法无证书运行时隐藏入口，保留普通发送。iPhone 默认 HTTP 入口不提供翻腕——Mac 控制台另出一张 HTTPS 配对码（内嵌 token，扫码即配对 + 拿到安全上下文一步到位），该码复用既有自签证书的一次性站点例外，不安装/不信任 CA。只有免手装证书且真机验收通过的入口才恢复提供。安卓也不能未经验证承诺 HTTP 可用。

用户说的“不在 iPhone 提供”仅指翻腕发送，不扩大为停止支持 iPhone 的输入、触控板或其他已支持功能。

## 2. 当前证据

- 用户安卓截图：下载证书后先选择打开程序，再被要求到系统设置安装，提供者显示 null。真实首次接入未完成。
- Web/settings.js 的 renderWristActions 无平台分流，输出 iPhone 描述文件和完全信任路径，安卓同样看到。
- Web/motion-send.js 在非安全上下文直接阻止开启；没有 requestPermission 时直接视为 granted，未以有效传感器事件证明可用。
- 本机 TLS 身份（Sources/SecureTransport，证书 CN=PocketDesk）已提供 46487/46488/46489 三个 HTTPS 端点；iOS 对其属自签，需一次性"访问此网站"站点例外，但不要求安装描述文件或开启完全信任。
- Web/pad.js 按页面端口推导控制端口；直接换成标准 HTTPS 域名仍可能连错控制地址。页面、控制、画面三个通道必须整体适配。
- Sources/Server.swift 存在本机回环免 token 的路径；新增反代必须先隔离手机入口，防止远端请求被当成本机请求。
- 之前安卓只授权就能用的具体地址、浏览器与有效发送证据尚未还原，不能编造原因。

## 3. 方案比较

| 方案 | 手机使用成本 | 开发与维护 | 结论 |
| --- | --- | --- | --- |
| A 默认网页按能力降级 | 扫码、正常发送；支持时主动开启翻腕并确认必要权限 | 最小；需能力状态、现有偏好迁移及真机验证 | 当前主方案 |
| B 经 Tailscale Serve 接入可信 HTTPS | 已入网用户扫码使用；电脑可能需首次同意启用 HTTPS | 三通道适配、鉴权隔离、证书生命周期与网络恢复验证 | **已否决（2026-09-11，用户决策：不靠谱）** |
| C 产品自管域名与自动证书 | 成功后可做到扫码使用，无手装 CA | 设备域名、独立私钥、签发续期、局域网解析、断网/换网和运维 | 当前不为单个手势功能投入 |

C 不必然要求桌面数据走公网：DNS-01 可验证不对公网暴露的服务域名，但产品仍要解决手机解析、连接、证书签发与续期。禁止把共享通配符私钥打包给所有电脑。没有域名、可信身份来源和生命周期方案时，不承诺纯离线首次接入也能自动获得公网信任。

原生手机应用可作为将来独立产品方向，但本期不为翻腕新增安装、分发与双端维护。PWA 或仅包一层网页不作为绕过浏览器权限的方案。

## 4. 用户路径与状态

首次扫码直接进入正常输入页面，不弹翻腕引导。默认关闭翻腕。非安全上下文隐藏翻腕整组，不出现证书下载、灰色开关或维修教程。

已具备安全上下文且接口存在时展示翻腕开关。用户主动开启后，在该次点击内请求需要的运动权限；随后只监听验证，不产生发送。以 3 秒为初始探测窗口，收到有限、非 null 的有效传感器数据后才启用识别；静止产生的合法零值不能算失败。具体时间通过双机实测校准。

权限拒绝或数据超时：开关回到关闭，就地一次提示“暂时无法使用翻腕发送，请使用发送按钮”，不循环弹权限、不要求系统配置。可由用户再次主动尝试。诊断细节归电脑端，手机不展示端口或证书术语。

恢复与退出：切后台、断线、失去控制权时停止识别；恢复连接重新验证有效数据，不自动请求权限。草稿为空、输入法组合中、提交中、设置面板打开时禁止候选发送。没有新手势不因恢复而发送。

已有开启偏好不能直接等同运行成功；能力不可用时本次停用。默认路径移除证书向导后，不删除用户已有证书或系统信任，也不把锁屏密码端点降到明文。锁屏功能与翻腕共享基础设施，另按自身安全门禁处理。

## 5. 可选可信连接的技术边界

Mac 控制台直出 HTTPS 配对码：该码指向 https://<局域网IP>:46487/?token=<Auth.token>，内嵌配对凭据，手机扫码即完成配对并拿到安全上下文（isSecureContext=true），翻腕入口随之出现。复用既有自签证书，iOS 仅需一次性"访问此网站"站点例外，不安装描述文件、不开完全信任，符合免证书红线。

候选结构：一个可信域名，页面与 API 走 HTTPS，控制和画面分别走同域 WSS 路径。服务端提供明确的端点配置，前端不继续用端口加一/加二猜测。需先证明 Serve 的 WebSocket Upgrade、路径转发及现有帧协议可用。

代理入口强制配对认证与控制租约，不享受回环豁免；电脑管理入口与手机入口隔离。不凭任意转发头认定请求安全或来自机主。锁屏端点若不能确认受保护通道就维持拒绝，不为通过测试取消保护。

域名改变意味着新的浏览器 origin：不能假定原 localStorage、配对状态、翻腕偏好和草稿自动迁移。迁移入口只在草稿与附件清空后允许重新扫码，避免未发送内容丢失。

只有页面、API、控制、画面全部验证后才生成面向用户的增强二维码。网络或证书异常时降级为翻腕不可用，不重新引导安装 CA；没有验证连通前不自动跳地址。

## 6. 实施阶段与退出条件

1. 真机基线：记录安卓当前浏览器、系统版本、页面协议、isSecureContext、权限接口和有效事件；iPhone Safari 同样记录。只做传感器诊断，不触发桌面发送。还原“安卓之前可用”的实际条件。
2. 主方案实施：撤出翻腕证书向导，建立环境/授权/数据/运行四种状态边界；已有偏好安全停用，普通发送始终可达。同步 Web L2/L3、README 与旧执行方案，明确替代其强制安装 CA 的要求。
3. HTTPS 配对码：Mac 控制台新增"安全连接·翻腕发送"二维码（/api/qr?type=secure），与既有 46387 控制页共享同一 token 与三通道（46487 控制页 / 46488 WSS / 46489 画面）。仅当本机 TLS 身份存在（secureURL 非空）时显示。已落地，待真机扫码验收。
4. 发布验收：只有真实手机完整走通才标注支持；未通过的 iPhone 不提供翻腕，不以浏览器模拟测试替代。

本期不承诺工期：阶段 1 的设备可访问性决定工作量；主方案不依赖增强路径完成，HTTPS 配对码已落地。

## 7. 验收标准

- 新手机无 PocketDesk CA、无证书下载、无系统信任操作即可完成本期对其宣称支持的路径；已有信任手机不能代替首次用户验收。
- 默认 HTTP：安卓/iPhone 普通输入发送正常，翻腕入口不诱导配置，不影响触控板和已支持的画面能力。
- 可信入口：首次必要权限只由用户点击触发；拒绝、无数据、断线、后台恢复均不误发。
- 每个支持组合连续 20 次明确翻腕只发送各一次；20 次输入、滚动、拿起手机和后台恢复操作不发送；结果是最低冒烟标准，不宣称统计可靠性。
- 验证未配对、错误 token、失去租约的 HTTP 与 WS 请求被拒；验证代理请求不能获得本机管理权限。
- 重启、睡眠唤醒、Wi-Fi/移动网络切换、证书不可用时不丢草稿、不重复发送、不要求装 CA。
- 如扩大实现为自动证书路线，签发失败、到期与续期失败是发布前额外必测项。
