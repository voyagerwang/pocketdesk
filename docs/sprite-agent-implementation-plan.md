# PocketDesk 小精灵：用户服务交付计划

> 2026-09-16，v1.2。M0–M2 技术链路已落地，但本轮审计结论是：**技术能力已存在，用户服务尚未成型**。本文改为用户服务交付计划；每一阶段必须交付一项用户能独立使用、能看见结果、能判断成败的服务，不再以「新增了模型/工具/API」作为阶段完成标志。
> 范围：现有手机 Web 首页的增量扩展，Operate 模式；沿用 DESIGN.md 的经典蓝/米白、目标栏、原生输入与画面工作台。不重做视觉系统。
> 优先级：本文规定小精灵入口的具体交互；voice-agent-browser-plan.md 提供浏览器集成背景；AGENT_PRODUCT_ARCHITECTURE.md 提供任务事实源、权限、证据与运行时契约。重叠交互以本文为准。


## 0. v1.2 产品审计（2026-09-16）
好你帮我安装一下 Codex Tools 这个应用，我需另要界面


### 0.1 审计范围与用户目标

审计的不是单张界面，而是完整服务旅程：进入小精灵 → 表达需求 → 看懂执行状态 → 必要时确认动作 → 获得可验证结果 → 追问或开始下一件事。目标是用户不需要理解 taskId、runtime、AX、工具调用或「串行任务」，也能始终知道：它在做什么、是否轮到我、最后有没有办成。

### 0.2 本轮真实流程结论

| 步骤 | 当前表现 | 健康度 | 结构性问题 |
| --- | --- | --- | --- |
| 1. 进入 | 默认选中小精灵，可直接输入 | 中 | 触控板占据首要位置，缺少「小精灵现在能为你做什么」的轻量引导 |
| 2. 提交 | 发送后出现任务卡 | 中 | 卡片排在触控板之后，视觉回执离操作点太远；发送提示在新任务后仍可残留 |
| 3. 执行 | 显示「执行中」 | 差 | 同时出现「放弃并保留草稿」和「新任务」；用户无法判断两者差别，「保留草稿」也与已提交任务的实际语义不符 |
| 4. 待确认 | 显示 URL 与拒绝/允许 | 差 | 状态已是「待确认」，下方却说「小精灵正在处理」；没用人话说清具体动作、目标和后果 |
| 5. 拒绝 | 任务先回到执行中，再给最终回答 | 中下 | 系统已知「未执行」，却仍让模型输出冗长解释，并夹带无关的前台浏览器错误 |
| 6. 完成/追问 | 显示最后回答，可输入追问 | 中 | 只看到最后结果，看不到「我刚才让它做什么」的紧凑上下文；「新任务」与直接继续输入的关系不清楚 |

### 0.3 根因

1. **信息架构仍以旧遥控器为中心**：小精灵只是被塞进触控板和快捷键之间，不是当前接收者下的主任务。
2. **把后端状态直接翻译成文案**：「执行中/待确认/已完成」没有回答用户此刻最关心的问题——「轮到我了吗？」。
3. **模型回答承担了本该由产品状态机承担的反馈**：允许、拒绝、打开成功等确定性事件仍要模型再解释一遍，又慢又噪。
4. **技术阶段代替了服务阶段**：M1 叫「只读」、M2 叫「浏览器写入」，但用户不买「读/写能力」，用户要的是「帮我看懂」、「帮我找到」、「帮我完成」。
5. **上下文采集过早**：AgentRunner 对新任务无条件读当前页，即使用户只是普通对话或拒绝一个动作，也会把「前台不是浏览器」带进回答。

### 0.4 交互修改决策（P0）

- 小精灵被选中时，顺序固定为：**接收者栏 → 任务/结果 → 输入 → 次要的触控板**。触控板不再隔开输入与结果。
- 无任务时只给一句能力说明和 2–3 个当前真能做的示例，不做能力广场，不展示尚未交付的承诺。
- 任务卡首行用人话表达进度：「已接到」「正在读取这个页面」「等你确认打开网页」「已打开」「未执行」「没能完成」；技术状态放进详情，不做主标题。
- 执行中只有一个退出动作：「不再等待」。隐藏「新任务」；只有终态才显示「新任务」。「保留草稿」从已发任务动作中删除。
- 任务运行时输入区仍可编辑并保留草稿，但发送按钮改为「等当前任务完成」并明确不可用；终态到达后自动变成「继续追问」，不吞草稿、不弹错。
- 确认卡必须是「动词 + 对象 + 后果」，例如「在默认浏览器新标签打开 example.com」；按钮为「暂不打开」/「打开」。待确认时禁止同时显示「正在处理」。
- 明确命令本身就是授权：用户原话明确包含「打开 + 具体网址/站点」时，可对该精确、可逆动作直接执行，不再二次确认；模型推断出的打开、目标不确定或将提交数据时仍必须确认。
- 拒绝、打开成功等确定性结果由任务状态机直接出卡，不再花一轮模型请求重述。模型只在需要综合、解释或继续推理时回答。
- 结果卡至少保留「用户要求摘要 + 最终结果 + 来源/产物 + 下一步」；旧轮次折叠，不做无限聊天气泡。
- 新任务必须清除旧 toast、旧错误和旧确认文案；它只解除当前任务上下文，不删历史。
- 新任务不再无条件读页面。只在用户明确说「这个网页/当前页/这篇内容」，或用户明确绑定页面时调 `read_page`；页面读取失败不得污染无关任务的回答。

### 0.5 新的服务交付路线（取代技术导向的 M1/M2/M3）

| 阶段 | 对用户可交付的服务 | 本阶段必须真实能做 | 交付验收 |
| --- | --- | --- | --- |
| S0 安心对话 | 「我可以把一件事交给小精灵，始终知道它做到哪了」 | 重排界面层级；修正状态文案/动作；草稿等待；刷新恢复；普通问答不读页面 | 10 轮普通问答+追问无无关页面报错；六种状态均能回答「现在谁行动」；手机刷新不丢任务 |
| S1 读懂当前页 | 「把我正在看的网页讲明白」 | 显式绑定当前页；摘要、提取要点、针对原页追问；来源和页面漂移可见 | 长文、动态页、切标签各 3 例；回答有来源，读错页面必须拦住；读不到时给可操作恢复方案 |
| S2 打开并找到 | 「帮我打开或搜索一个公开信息」 | 精确打开 URL/站点；搜索查询；读回打开结果；明确授权不重复问 | 「打开百度」「搜索今日天气并总结」等 10 例；系统证据确认实际打开/搜索，不以模型口头声称为准 |
| S3 完成一个网页流程 | 「在测试环境里替我填好并提交一件事」 | 读取结构、点击/填写、统一控制权、提交前具体确认、提交后读回核验、人工接管/继续 | 只用一个自有测试表单作首个黄金流程；成功、校验错误、用户拒绝、中途接管全覆盖；不触碰生产发布/付款 |
| S4 交付到一个桌面应用 | 「把明确内容送到我选定的应用，并说清送到了哪」 | 先选一个可验收的目标应用/测试会话；打开、输入、提交分开；目标标题/输入位置/提交结果证据 | 不把「发出按键」写成「对方已收到」；20 轮真实投递无错目标、无重复、无跨任务串文 |
| S5 用资料产出交付物 | 「给小精灵一份资料，拿回一份可用的结果」 | 附件/图片、产物持久地址、预览/下载、失败不丢输入；只选一类产物先做深 | 例如「把这篇长文整理成会议纪要」；用户能看、能下载、能继续改，而不是只得到一段聊天文字 |

### 0.6 阶段门禁

- 上一阶段没有用户可见的完整服务和真实验收证据，不开始下一阶段。
- 每阶段只能有一个黄金任务流；先把成功、失败、拒绝、断线恢复做完，再扩能力数量。
- 验收证据必须包含：真机流程截图、任务事件记录、最终产物/目标读回，以及未通过项。模型说「完成了」不是证据。
- 只有交互验收通过才能写「可发布」；编译通过、API 存在、模型能调用工具只能证明实现进展。
- 任何新能力都要先回答「它向用户交付什么服务」；回答不出来就不进计划。

## 1. 交付目标

用户打开 PocketDesk，选中小精灵，使用手机输入法打字或听写，轻甩或点发送，任务在 Mac 上交给 Agent；结果回到手机，继续输入即可追问。需要自己操作时展开原有触控板或查看电脑画面。

完整交付必须包含真实 Agent 接入和结果回传。只有图标、聊天气泡、模拟回答或向桌面应用粘贴文字，不能算完成。

| 项目    | 决策                                          |
| ----- | ------------------------------------------- |

| 默认入口  | 正常新开首页跟随电脑前台；手动进入小精灵暂缓跟随；同页面后台返回保留当前目标和草稿          |

| 键盘    | 点小精灵立即尝试唤起；初次加载尽力聚焦，受限时一点输入                 |
| 提交    | 按钮和现有轻甩识别共用业务入口                             |
| 触控板   | 保留，默认收起；展开时收键盘，收起后可回输入                      |
| 任务    | 一个执行中的任务；结果可继续追问，也可显式新任务                    |

图标排序与默认选中互相独立：小精灵可以排第一，启动仍跟随真实电脑前台。手动进入小精灵后暂停跟随，通过输入栏「跟随电脑」恢复；有未发送内容时先保留草稿并提示发送或清空。应用侧输入栏提供「回到小精灵」，只改变手机接收者，不中断桌面任务。首版保持串行、纯文字任务。

## 2. 首页布局与状态

示意布局，不是新增页面：

```text
PocketDesk                  连接状态  设置
[小精灵] [应用 A] [应用 B] [应用 C] …

小精灵 · 当前任务（有任务时显示）
正在读取网页 / 简短结果 / 需要补充的问题
[来源链接]       [查看画面] [停止或接管]

[当前网页：标题 · 域名 ×]（绑定后显示）
[告诉小精灵，你想做什么……             ]
[新任务]                         [发送给小精灵]

[触控板：点按展开]
```

- 空状态不展示大段介绍、能力广场或第二个聊天输入框；一句占位提示即可。
- 任务卡只显示当前任务，已完成内容可展开；历史从次级入口进入，不能无限挤压编辑区。
- 小精灵使用本地 SVG 资产，与已有图标尺寸/选中态一致；不使用 emoji、外部字体或 CDN。
- 连接状态分开表达：Mac 连接、Agent 可用、浏览器工具可用。Mac 已连接不等于小精灵可工作；普通聊天不依赖录屏/辅助功能授权。
- 正文和错误可读，状态不只靠颜色；按钮命中区至少 44px；沿用现有字号和间距令牌。
- 键盘展开时编辑区与发送按钮保持可见，结果区可滚动；遵守 VisualViewport 与安全区。用户在读旧结果时，新事件不强制滚到底。
- **M1 不得显示「停止」（v1.1 修正）**：示意布局里的「停止或接管」是 M2 起的能力目标。M1 的 runtime 大概率不支持真正的取消，此时卡片只能显示「放弃并保留草稿」，并在设置/提示里说明「已派发的任务仍会在 Mac 上跑完」。谎报「已停止」违反 §7 的红线。
- 普通应用选中时恢复现有面板，不展示小精灵工具按钮；后台任务只在小精灵图标上显示轻量状态，不自动跳回。

## 3. 目标模型：系统入口与桌面应用分开

拟议逻辑模型：`Recipient = app(targetId) | agent(sprite)`。小精灵属于内置接收者，不伪装成有 bundleID、appURL 的 macOS 应用。

- 不把小精灵写入 TargetStore 的普通应用列表，不调用 AppDiscovery、/api/activate、鼠标定位或 AX 输入绑定。
- 小精灵与普通应用共用同一套排序交互，用户可把它移到任何位置；首次加入且尚无排序记录时插入第一位，之后启动、刷新和配置同步都尊重用户保存的顺序。首版不增加多个 Agent 图标。
- 使用独立的接收者顺序（例如 `recipientOrder`，保存稳定的 agent/app 引用），不为排序把小精灵塞进普通应用配置。沿用现有电脑控制台排序入口和持久化通道，手机同步展示；控制台必须将小精灵列为可排序项。首版不另建手机拖拽排序系统。
- 旧数据迁移只执行一次：小精灵插入首位，普通应用原相对顺序不变。删除应用清除对应顺序引用，新增应用沿现有规则追加，重复/未知引用校验清理；不得每次读取重新把小精灵置顶。
- recipients.js 管理渲染、选择与前台跟随，app.js 编排启动和心跳；快捷键按 recipient 类型分支。桌面前台变化不得把手动选中的小精灵切走。
- 首次加载普通应用配置失败时，能显示小精灵入口及真实离线状态；不得默认激活某个桌面应用。
- 手机接收者和 Mac 前台应用是两种状态，不共用一个变量表达。

## 4. 键盘与面板契约

### 点击小精灵

在用户点击事件的同步调用链内完成：选择接收者、显示原生输入框、聚焦输入框。网络状态请求随后执行，不能 await 后才 focus。已选小精灵再点一次只回到输入并聚焦，不清草稿、不新建任务。

首次页面加载尝试 focus，但不能承诺所有浏览器都会打开软键盘。没有弹出时让输入框直接可点，不循环 blur/focus、不定时抢焦点。用户主动收起键盘后，任务回执、页面心跳和后台返回都不得再次强制弹出。

首版只唤起手机键盘，不能自动启动键盘内的语音听写。语音按钮、浮动键盘形态由输入法控制。

WebKit 官方记录说明程序化 focus 和软键盘弹出存在用户手势及宿主差异；具体以目标真机验收为准：[焦点限制](https://bugs.webkit.org/show_bug.cgi?id=195884)、[WKWebView 宿主相关变更](https://bugs.webkit.org/show_bug.cgi?id=243416)。不能把后者推断为 Safari 网页无条件自动弹键盘。

### 触控板与全屏

触控板沿用现有位置和手势。展开不改变接收者、不清空草稿，也不自动发送任务。查看 PiP 只观看，不取得写入权。全屏键盘仍沿用当前 recipient，并明确标注「发送给小精灵」或应用名；绝不能在全屏悄悄从 AI 模式变成电脑实时输入。

若用户需要向电脑应用打字，应显式选择应用；查看画面、点击画面或隐藏输入框不能自动改变接收者。

## 5. 草稿与切换：避免误发送

同一个可见编辑框，底层至少分开保存 `agentDraft` 与现有 `appDraft`。不强制改造普通应用之间既有草稿迁移规则。

- 小精灵草稿仅保留在手机编辑状态；发送前不调用 /api/live-input、/api/send、/api/input-context，也不写剪贴板。
- 应用 → 小精灵：封存应用草稿，取消未发送的镜像队列/恢复定时器，失效旧选择代际；已在途的写入不能假称撤回。电脑已有文字不删除。恢复独立 AI 草稿。
- 小精灵 → 应用：保存 AI 草稿，恢复应用草稿，再按现有规则显式绑定应用；严禁把 AI 指令灌进目标输入框。
- 切换时的旧回执只能更新自己的草稿/任务记录，不能清空新目标输入、改变新选中项或覆盖提示。
- 提交瞬间固定 recipient、draftId/revision、requestId、正文和上下文；等待期间切换目标也不得改变本次去向。
- 为防输入法迟到事件，沿用已有 IME 代际隔离。复用不等于直接调用会重新聚焦或同步应用的完整 clearCompose；应抽取无桌面副作用的编辑收尾能力。
- AI 提交确认前冻结该快照；确认任务已持久接收后才清当前匹配草稿。失败保留正文。请求超时先按 requestId 查账，不生成新 ID 盲重发。
- 首版 AI 输入仅文字；切到小精灵时隐藏图片添加，应用附件仍保留在应用草稿。后续有经过验证的多模态 runtime 再接任务附件，不复用会消费桌面粘贴批次的语义。
- 「清空草稿」只清 AI 未发文字；「新任务」解除当前任务关联、建立空草稿，旧未发文字存在时先收存可恢复，不删除历史、不取消旧任务、不调用电脑清空接口。

## 6. 统一发送与轻甩

保留 `pocketdeskComposeSend` 为统一业务提交入口；禁止覆盖 `pocketdeskSend`，后者属于指针/画面控制消息。

```text
发送按钮 / 轻甩候选 / 合适的发送快捷入口
              ↓
       同一发送门禁与提交锁
              ↓ 固定接收者与草稿快照
     app → 原输入执行链路
   agent → AgentClient → Mac TaskService
```

轻甩沿用 motion-recognizer.js 当前「前倾并停稳」识别与设置，不额外实现泛摇晃识别，不改变灵敏度。用户口语“轻甩”不代表任意震动都发送。

共同门禁：有非空草稿、前台可见、无设置/模态层、输入法组合结束、最近输入稳定、无提交锁、网络和相关能力就绪、当前控制会话合格。体感仍沿用现有传感器权限、有效数据验证及失控挂起规则。

- app 分支继续检查 livePaused/liveProbing 等草稿绑定状态。
- agent 分支不能因旧 app 的 livePaused 或缺少 AX 焦点而被阻塞。
- 触控板拖动、全屏手势期间不触发体感提交。
- 轻甩与按钮同刻发生，由同一快照锁和服务端 requestId 去重，最终最多一条用户消息。
- 无内容时轻甩不创建空任务，也不发送回车到电脑。
- 轻甩只表示“提交这段话”，不能当成发布/删除授权弹层的确认键。
- 传感器不支持/未授权/无有效数据时按钮仍可用；保留现有免证书降级，不要求安装 CA。
- 接收回执不是任务完成。清草稿后可继续写下一句话；是否可提交由下一节运行状态决定。

## 7. 对话与任务状态

复用整体方案的 Task/Attempt 词汇，首版手机简化为：待提交、已接收、执行中、待补充、暂停中、已暂停、停止中、已停止、已完成、失败、结果待核对。

| 状态     | 再次输入与发送                                         | 卡片动作         |
| ------ | ----------------------------------------------- | ------------ |
| 无任务    | 创建新 taskId                                      | 发送           |
| 待补充    | 同 taskId 添加用户消息后继续                              | 发送、停止        |
| 执行中    | 可编辑；runtime 支持有确认的 supplement 才能发，否则保留草稿提示完成后发送 | 停止、查看、接管     |
| 已完成    | 默认同 taskId 追问，建立新 turn/attempt                  | 追问、新任务、来源    |
| 已暂停    | 草稿可编辑；显式继续前重新观察                                 | 继续、停止        |
| 失败/不确定 | 先核验旧 attempt，不自动重放有副作用步骤                        | 查看原因、核验或明确重试 |

首版一个活动执行任务。用户点新任务可开始编辑，旧任务未结束时新任务不暗中并行；提交处明确需结束旧任务。切换应用、收起输入或关闭手机页面不等于取消任务。

任务结果由 runtime 返回，包含回答和来源/产物引用；页面真实写入要读回目标状态。阶段消息按实际事件产生，不用倒计时假装进度。断线后依据事件游标补取并恢复同一 taskId。

停止只提交取消意图，待执行器确认才显示已停止；不支持取消时显示真实能力限制，并停止本地后续步骤。已经提交到外部系统的动作不会因停止回滚。

## 8. Agent 与浏览器的职责

```text
小精灵输入 → 已鉴权 Task API → 唯一任务存储 → Agent runtime
                                                 ├─ BrowserAdapter → tt-bridge → Chrome
                                                 └─ 已批准的本地/系统工具
任务状态与结果 ← 查询/事件补取 ← 持久任务与事件记录
```

小精灵是产品入口名称，不是固定模型名。首版只实现一个真实 runtime adapter；要求结构化派单、任务身份、结果回传、续接、错误分类，取消/事件/用量则声明实际能力。


### 8.1 模型适配层（v1.1 决策）

`ModelAdapter` 只负责「把 PocketDesk 的任务/工具协议翻译成某家 HTTP 协议并解析回结构化结果」，**不持有工具执行权**。工具一律由 PocketDesk 本地执行后把结果回传模型，模型不能直接操作电脑。

- 首版协议：OpenAI 兼容 `POST /chat/completions`（含 tools/function calling 与 tool 结果回传）。Base URL、API Key、模型名三项由控制台配置，存 Mac 钥匙串或受保护配置文件，**不写日志、不下发到手机**。
- 适配层必须可替换：新增厂商只加一个 `ModelAdapter` 实现，不改 TaskService/AgentAdapter。首版不实现多模型路由与自动降级。
- 专用 Computer Use（截图→动作循环）是后续独立能力，不作为 M1 基础功能的前置条件；不因为某家提供了 Computer Use 就绕过 §10 的写入仲裁。

M0 先验证运行时，再实施真实任务链。没有正式接口时不能扫描桌面应用内部凭证或用模拟数据交付。若只能 GUI 投递，必须标记「已投递，无法回收结果」，不达到本方案完整交付标准。M0 的运行时验证清单见 §12。

BrowserAdapter、AgentAdapter、ModelAdapter 三者分开。tt-bridge 只是浏览器工具，许可与可维护性评估沿前置方案；商业内置必须先解决 CC BY-NC 限制。它的 daemon 不直接暴露到手机网络。

**网页正文读取走 tt-bridge（BrowserAdapter 隔离，v1.1 决策）**：M1 先核验标签页绑定、正文读取与断线行为；许可或技术验证不满足再比较替代方案。macOS AX 的定位是桌面应用观察与辅助（见 §15），**不因为已有 InputFocus 焦点探测代码就默认让它承担网页正文读取**——两者失败模式和数据质量不同，不能混用同一条证据链。

“当前网页”在任务提交时采集绑定引用；显示标题/域名，并保留 browser/window/tabId/URL/observedAt。找不到确定页面或多个候选时请用户选择；执行前确认目标没有漂移，不默认操作后来切到的页面。选网页、读上下文的范围来自用户任务，不持续上传所有标签页或桌面视频。

网页内容只作为资料，不能改变工具权限、用户规则和任务授权。网页任务优先 DOM/结构化读取，现有 JPEG 流服务人工查看，不逐帧喂给模型。


## 9. 最小接口与持久化契约（新增建议，非现状）

沿整体方案使用 `/api/v1`，全部任务读写鉴权，包括回环调用；不要沿用普通本机写请求自动豁免到敏感任务接口。按配对主体限制对象访问，手机不持有模型密钥。

| 接口                                      | 必要行为                                                                |
| --------------------------------------- | ------------------------------------------------------------------- |
| GET /api/v1/executors                   | 返回 agent/browser 可用性和已验证 capabilities                               |
| POST /api/v1/tasks                      | requestId、recipient、text、contextRefs；持久接受后返回 taskId/revision/status |
| GET /api/v1/tasks/by-request/:requestId | 解决提交超时，限定调用主体；找回原 taskId                                            |
| GET /api/v1/tasks/:id                   | 当前快照、messages、状态、证据、来源及可用动作                                         |
| GET /api/v1/tasks/:id/events?after=seq  | 单调事件序列，缺口时返回需刷新快照                                                   |
| POST /api/v1/tasks/:id/actions          | supplement/resume/cancel/takeover；requestId、expectedRevision 和相应参数  |
| GET /api/v1/tasks?cursor=...            | 当前主体的历史摘要，分页，不返回全部正文                                                |

- 请求去重键为主体 + requestId；相同键不同内容返回冲突，同内容返回原结果。接受和事件写入在同一事务内。
- body 中不接受任意 shell 指令或不受限制的工具定义。runtime 凭证放 Mac 钥匙串，不写日志、静态文件或手机 localStorage。
- **首版存储用文件化方案，不用 SQLite（v1.1 修正）**：本项目无 Package.swift，由 `scripts/install-app.sh` 直接 `swiftc` 裸编且未链接 `-lsqlite3`，引入 SQLite 要改构建并手写 C API 封装，成本与收益不匹配。首版沿用 TargetStore 风格：`tasks.json`（原子整体写）+ `events.jsonl`（append-only 事件日志）+ `dedupe.json`（requestId 去重）。schemaVersion 与迁移策略照旧要求；确有并发/查询压力时再评估换成 SQLite，届时同步改构建脚本。不能让两边各自声明权威。
- 启动时恢复任务记录；已派发但状态未知进入核验，不自动重新执行。明确 schemaVersion、迁移与回滚兼容策略。
- **鉴权豁免方向必须反转（v1.1 修正）**：`Sources/Server.swift` 现有判定是「回环一律免 Bearer」。`/api/v1` 要求含回环在内全部鉴权，因此路由分类要显式把 `/api/v1/` 排除出回环豁免，否则本机任意进程可读取全部任务正文。
- 首版用轻量增量轮询即可；任务事件不能放入光标 latest-only 队列。记录实际用量，执行器不提供时显示 unknown。
- **轮询与超时默认值（v1.1 补充，集中配置并在设置中可见）**：轮询 2s 起、连续无事件按 1.5 倍退避至上限 10s；任务软超时 5 分钟（提示但可继续等），硬超时 10 分钟（停止等待、进入核验）；单任务 supplement 最多 5 轮；事件游标单任务保留上限 2000 条，超出要求刷新快照。
- 初始限额：单条输入 16 KiB UTF-8，超限保留草稿并提示；一次仅一个活动执行。任务与事件保留 30 天，用户可清理；这些值集中配置并在设置说明中可见。
- 回答按纯文本或经过清理的 Markdown 呈现；禁止网页/模型返回的 HTML 或脚本直接执行。产物必须使用已鉴权可访问链接，不能给手机一个 Mac 绝对路径。

## 10. 保留触控板时的控制权仲裁

任务控制者与手机控制者不能同时写同一电脑。tt-bridge 绕过 CGEvent，因此仅复用现有 WSServer 手机租约还不够。

1. 所有 Agent 浏览器写操作在发出前检查同一 ControlArbiter 的 owner、scope、generation；不能保留旁路 CLI 执行入口。
2. 手机展开触控板时，若 Agent 正在控制电脑，先申请接管，显示「正在接管」；等待停止新写入并处理在途命令，确认后才开启触控板。
3. 接管过程中发生的触摸不缓存、不补发。查看画面无需接管，真正操作前必须取得控制权。
4. 无法确认停止在途写入的适配器不能显示「可安全接管」；说明仍在结束当前操作。M0 无法建立可用隔离边界时，M2 的写入能力不得启用。
5. 回交只经「继续任务」，重新读取网页/画面、目标和任务 revision。禁止自动追赶旧点击序列。
6. 用户切到普通应用并准备输入也属于人工写入，必须经过同一仲裁；不能只拦触控板漏掉实时输入和快捷键。
7. 实体鼠标/键盘接管属于额外检测能力，未实现时不宣称全局自动感知。优先提供显式停止和接管入口。

## 12. 分阶段交付与退出条件

### M0 能力验证

未通过前只能开发明确标识的测试夹具，不发布假就绪 UI。每项输出：版本、命令或 API 证据、实际结果、未支持能力。

**A. 模型运行时（OpenAI 兼容接口，v1.1）**

1. 用一个可配置三元组（Base URL / API Key / 模型名）打通一次真实调用，拿到可解析的结构化结果。
2. 工具调用闭环：模型请求工具 → PocketDesk 本地执行 → 回传 tool 结果 → 模型给出最终回答。**工具执行权必须在 PocketDesk 侧**，模型不能直连电脑。
3. 续接：同一 taskId 下追问（历史消息回放）能拿到上下文相关回答。
4. 取消：中断 HTTP 请求/进程后任务真的停止，不出现「前端显示已停、后台继续烧 token」。
5. 用量与错误分类：能读到 usage；超时/限流/鉴权失败/内容错误可区分。读不到就记 unknown。
6. 视觉能力按需验证，**不作为 M1 前置**。

**B. 浏览器读取（tt-bridge，v1.1）**

1. 指定标签页绑定：能否按 tabId/URL 定位到确定页面并读取正文与标题。
2. 正文质量：读一个长文档页和一个动态渲染页，记录截断、缺失、噪音比例。
3. 断线行为：扩展或 daemon 掉线后能否检测、重连、明确报错。
4. 许可：CC BY-NC 对内置分发的处理结论（**未解决前不进入 M1 交付**）。
5. 写入停止边界：见 §10；M0 无法建立可用隔离边界时 M2 写入能力不得启用。

**C. 代码基线**

1. 提交当前 16 个未提交改动（Server.swift、InputExecutor、InputFocus 等），作为回归基线。
2. 现有测试全绿，普通应用实时输入/图片/轻甩/指针/PiP 的真实回保持不变——它是 M1 回归的对照物。

**M0-B 结论（偏离，已记录）**：tt-bridge 五项**未做**，卡在第 4 项 CC BY-NC 许可——它与 PocketDesk 的 MIT 内置分发冲突，不是今晚能定的法律判断。按 §8.1 的 BrowserAdapter 隔离，**M1 的网页正文读取改走自有 macOS AX**（`Sources/PageReader.swift`）：零新依赖、零许可风险、可立即交付真实只读能力。tt-bridge 降为 M2 写入阶段的候选实现，接口一致，替换不动 TaskService。**这条偏离的代价要如实记录**：AX 方案拿不到 tabId（绑定引用只有 windowId + URL + 标题），正文质量依赖页面可访问性树的完整度，长文档与动态渲染页的截断/噪音比例尚未在真机上量化——M2 评估 tt-bridge 时应拿这份数据对比。

### 15.1 三层能力，不按软件数量重复造工具

1. **现有基础动作**：将 TargetStore 的真实应用列表、应用激活、输入、提交和快捷键封装成 NativeActionAdapter。明确打开请求可直接按已配置 ID 解析执行；输入和提交需通过目标及控制权核验。源码默认目标含微信、WorkBuddy、飞书、ChatGPT、ZCode、Chrome、UU。Cola 是否已经配置以当前 targets 为准，不由名字猜 bundleID。
2. **界面理解与流程**：读取指定窗口的 AX 可访问性树（按钮、输入框等结构）及必要截图，识别联系人、对话标题、输入框与结果。它补充现有 InputFocus 的焦点核验，不将现有局部 AX 探针误称完整桌面观察能力。
3. **业务接口/任务接口**：有稳定 API/CLI 时直接对接，如飞书发送或真正的 Agent 派单。向 WorkBuddy/Cola 输入一段话，只证明 GUI 投递；回收执行进度、最终结果和取消仍需正式接口或单独验证的界面观察流程。

新增应用不应自动获得“任意操作”能力。应用发现返回真实 ID，能力记录分 open/type/submit/observe/findRecipient/verifyResult，包含测试版本、日期与限制。首版不用为每个软件建独立 Agent。

### 15.2 微信的两种任务

- “搜索张三并发送”：新增搜索入口定位、候选读取、同名辨别、会话标题核验、输入和提交后观察。优先 AX，缺少可读元素时用截图/视觉；看不清或重名无法区分时让用户选择。
- 首个验证场景使用用户自有测试会话（例如文件传输助手），发送内容仍需用户明确授权。没有实测前不承诺某版
- 什本微信稳定兼容。
- 本方案不依赖微信协议破解、进程注入或私有数据库读取；通用桌面路径不预设个人微信存在官方任意联系人发信 API。

### 15.3 与浏览器桥对应的桌面桥

```text
小精灵 Agent
 ├─ NativeActionAdapter → 现有 PocketDesk 应用/输入能力
 ├─ BrowserAdapter → tt-bridge 等浏览器工具
 ├─ DesktopAdapter → AX 观察 + 按需截图 + 受仲裁的桌面动作
 └─ ServiceAdapter → 飞书等正式业务接口
```

模型决定下一步，本地桥执行并返回新观察：观察 → 决策 → 执行 → 再观察 → 核验或下一步。最小桌面工具为 apps.list、app.open、desktop.observe、desktop.act；act 用结构化动作和绑定目标，不暴露任意 shell。常用已验证流程可再封装 chat.findRecipient 等语义工具。

观察包含 appId/PID/windowId、snapshotId、坐标尺寸、显示器与缩放信息、时间和可用元素。元素引用及坐标必须绑定快照；窗口移动、过期或控制代际变化时重取。截图发送给模型是新增数据流，只取任务所需窗口/区域，不复用持续视频上传。

输入必须区分 type 与 submit：搜索框填词不能调用自带 Return 的发送动作；模型请求一次 type 加一次 key 时，适配层不能在 type 内额外按 Return。拆分沿用现有执行器内部能力，不重复粘贴/键盘实现。

## 飞书 CLI 首版（2026-09-18）
PocketDesk 独立调用与 Workbench 相同用户环境的 lark-cli，不复制令牌、不要求 Workbench 在线。首版仅单人纯文本：feishu_message 搜索联系人，唯一命中发送；同名进入 needsInput，让用户口述序号/部门后续接。发送固定 --as user，持久尝试记录与任务 ID 幂等键，未知结果不自动重发；取得 message_id 才显示已发送。尚未实现群发、附件和 CLI 会话到桌面会话的自动接续。授权由 CLI 管理，缺 scope 时增量补授权。

## 飞书能力扩展（2026-09-18，覆盖首版单聊限制）

- feishu_message 增加 kind=group：按群名搜索、同名选择，唯一目标用 chat_id 发送，不再只支持单聊。
- feishu_help 返回真实授权范围与 CLI 各业务域帮助，支持 Schema 与 CLI 嵌入规范；feishu_execute 按查到的参数执行。消息、群成员、文档、云盘、表格、知识库、任务、邮箱、审批、会议等不再逐一等待 PocketDesk 写专用工具；实际可用性仍由 CLI 身份和 scope 决定。
- 默认本人身份，配置/profile/auth 管理不作为模型业务工具；不读取或复制凭证、不开放 shell。普通明确写请求直接执行，高风险遵循 CLI 确认；写前持久记录，未知不自动重试。多个接收者/复杂消息通过通用工具逐一核验后执行。
- 当前账户核验 198 项 scopes；这不等于每个业务域全权限。真实群列表、授权与帮助读取已验证，写入与高风险通过隔离替身验证，没有实际向群/联系人发测试消息。
