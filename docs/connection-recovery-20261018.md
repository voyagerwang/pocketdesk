# 手机浏览器连接恢复 · 2026-10-18

> L2 | 父级: CLAUDE.md

## 现场事实

- 用户报告手机浏览器／扫码网页再次无法连接。
- Mac 当前连接 `<家庭Wi-Fi-5G>`，Wi-Fi 使用硬件 MAC `<硬件MAC-已脱敏>`，私有地址关闭，DHCP 分配 `192.168.31.x`；该网络自动加入开启。
- `VoiceDeck` 进程正常，HTTP、控制 WS、画面 WS 分别监听 46387–46389，安全通道亦在监听。回环及 `.197` 的普通首页均返回 200；旧 `.123` 地址请求超时、ARP 未解析。防火墙关闭，没有将重启服务当成修复。
- 当前控制台生成 `.197` 的默认扫码入口。本机能解析电脑名称，不能据此断言手机也支持 `.local`。
- 原先使用的 `.123` 与另一条 Wi-Fi 的固定私有地址不同。地址保留必须匹配实际 SSID 使用的 MAC；路由器相同不等于电脑身份或租约相同。手机失败页面的实际 URL 尚未直接取得，换网与旧入口失效已证实，手机端因果仍需复测。

## 代码边界

`Web/app.js` 原先只在首次启动成功后启动心跳；首次状态请求失败时不会完成后续初始化。心跳还缺少整体读取截止时间和单个在途事务，可能在挂起时重复排请求。HTTP 可达、控制 WS 未就绪时，连接徽标也会误报就绪。

修复沿用现有启动、心跳和 `pad.js` 控制事实：首次失败继续重试并完成初始化，状态及响应体读取使用 4.5 秒截止，同一时刻只有一个连接事务，停止/超时后迟到回包作废，控制关闭即撤下就绪状态。首次 HTTP 未确认时，WS 认证也不能提前显示就绪。首次成功立即登记配对心跳；只读任务恢复不阻塞基础连接。初次失败期间新增的草稿/附件保留，恢复时不自动绑定新前台，等待用户选择接收者；输入和任务仍遵循原有发送门禁，不以重连重放提交。

浏览器代码只在当前 origin 内恢复连接，不能从失效数字 IP 自动发现新 IP。稳定数字书签需要稳定网络及相符的 DHCP 保留；换网使用当前电脑控制台重新扫码。现有草稿不跨 origin 自动迁移。

## 部署与验收

本轮仅升级已安装 App 的 `Web/app.js` 和 `Web/index.html`；资源版本 `3.0.35-connection`。先备份已安装 App，以该安装版克隆为基线替换资源、按既有 designated requirement 重签并验签，再交接原 launchd 服务。避免将工作区其他未提交的 Swift 改动编入本次连接修复。

实际网络恢复：关闭 `<家庭Wi-Fi-5G>` 的自动加入时系统要求认证，用户完成触控 ID 后设置流程返回主页面；首次切回 `<家庭Wi-Fi>` 加入失败，系统短暂接入另一已存网络，第二次连接成功。系统详情读回 `<家庭Wi-Fi>` 已连接、自动加入开启、私有地址“固定”、MAC `<私有MAC-已脱敏>`、IP `192.168.31.x`。DHCP 与控制台返回的地址一致，原地址首页恢复 HTTP 200。5GHz 关闭操作已提交，最终独立读回其开关受系统 UI 超时影响未完成；本轮没有改路由器的 DHCP 列表，也未删除其他已保存网络。

用户随后确认手机页面“能打开，但还没有已就绪”。继续只读核验：`accessibility=true`，三个普通端口和三个安全端口均监听，但 `phoneLastSeen=0`、无在线设备；带既有有效凭证和真实同源请求头的 LAN `/api/status`、`/api/recipients` 均返回 200，`/api/pair` 服务实现返回 JSON `{ok:true}`，新启动读取与现有协议兼容。尚无证据证明是控制 WS 单独失败，因为新页面成功执行 HTTP 配对时应先记录手机在线。

因此补发由电脑当前 `/api/qr?type=ip` 生成的完整连接码，并明确裸 IP 网址不含首次配对凭证；新的浏览器、扫码容器或清空站点存储后需扫码。缺少/失效凭证是当时的诊断假设，没有取得原失败页面文案，不把“页面打开”当作配对成功。

最终真机结果：补发完整连接码后，用户明确回复“已经可以了”。随即独立读取电脑状态，当前地址仍为 `http://192.168.31.x:46387`、辅助功能已授权，手机心跳距读取时 3 秒；设备记录显示 `<安卓机型> / Android / Chrome` 为 `online=true` 且 `controlling=true`。至此确认手机实际连通、配对登记和控制租约恢复；未代用户注入文字或点击桌面。长期睡眠恢复和切换其他 Wi-Fi 的稳定性仍未在本轮实机验证，不承诺数字 IP 可跨网络不变。
