# PocketDesk 电脑反馈与 TTS 支持方案

> 2026-09-18；调研与实施建议，尚未实现。依据当前工作区代码与厂商官方文档。
> 用户目标：手机承担输入，电脑展示小精灵的反馈；之后可直接听回复，不必低头看手机。
> [PROTOCOL]: 变更时更新此头部，然后检查 CLAUDE.md

## 1. 结论与范围

先建立电脑上的文字对话反馈，再让 TTS 消费同一条回复。继续使用手机输入法听写，不新增 ASR、常听麦克风或 Realtime 会话。默认场景是用户能看见 Mac 屏幕，声音由 Mac 或其连接的耳机输出；离开电脑后的手机音频回传另行设计。

首期覆盖 PocketDesk 自己的小精灵回复、追问和执行回执。WorkBuddy 等外部应用的回答回传是独立接入能力，不能因接上 TTS 就宣称已经支持。

## 2. 对已有调研的复核

已读 `voice-solution-research.md`。保留“语音作为现有文本 Agent 的 I/O 层”和“本地优先、云端可替换”的方向，调整落地顺序：

- 用户已有手机听写；ASR 不是此次反馈能力的前置条件。
- 不先部署 Whisper、ChatTTS 或其他本地大模型。系统语音足以验证闭环，中文自然度需真机试听。
- 原文的主观音质分数、跨厂商延迟、价格与部分模型名称缺少具体官方出处，本方案不采纳为采购依据，也未对整份 ASR/Realtime 表做逐项审计。
- “本地 TTS”只描述朗读环节；现有 Agent 模型请求仍可能联网，不能因此声称整个助手离线可用。

## 4. 官方实践及采用方式

1. **文字和语音使用同一条对话。** LiveKit 支持文字输入输出、纯文本会话与音频开关，并处理语音与转写同步。PocketDesk 借鉴这种分离方式，无须为当前单机需求引入整个 LiveKit。[官方文档](https://docs.livekit.io/agents/multimodality/text/)
2. **打断要清理播放队列。** LiveKit 的中断处理会停止语音，并区分用户实际听到的部分。PocketDesk 保留完整文字，只记录朗读中断位置，不假定未播放内容已被用户听到。[官方文档](https://docs.livekit.io/agents/logic/turns/)
3. **流式 TTS 不等于模型流式回复。** ElevenLabs 区分完整文本输入的 HTTP 流式音频与增量文本输入的 WebSocket；分块大小影响韵律与延迟。先解决现有完整结果朗读，后续再改模型流和句子切分。[官方文档](https://elevenlabs.io/docs/eleven-api/concepts/audio-streaming)
4. **原生反馈窗不激活应用。** Apple 提供 NSPanel 与 nonactivatingPanel 样式。它是实现基础；不抢键盘焦点仍需配置和实测，不能只设置一个标志就宣布通过。[官方文档](https://developer.apple.com/documentation/appkit/nswindow/stylemask-swift.struct)
5. **系统 TTS 已有说话、暂停、停止能力。** AVSpeechSynthesizer 可用于首版，启动时检查可用中文音色，缺失或失败时保留文字。[官方文档](https://developer.apple.com/documentation/avfaudio/avspeechsynthesizer)
6. **避免重复打扰。** Apple 通知指南反对同一事项反复通知。因此过程状态原位更新，需要回答和最终结果才提高显著性。[官方指南](https://developer.apple.com/design/human-interface-guidelines/notifications)
7. **云端中文音色候选。** 火山引擎官方提供语音合成与双向流式能力，可作为下一阶段候选；本次未做账户接入、费用核算或中文音质比较。[官方产品页](https://www.volcengine.com/product/TTS)

## 5. 用户实际会看到什么

建议在电脑屏幕边缘显示一个可收起、可固定位置的小对话窗，沿用项目经典蓝/米白身份和系统可读字体。它承载反馈，不复制整套手机控制台；布局与视觉稿留待实施时确认。

| 场景 | 电脑文字 | 语音策略 |
|---|---|---|
| 手机已提交 | 用户这句话 + 已接收 | 默认不念一遍用户输入 |
| 正在执行 | 一条原位更新的真实状态 | 默认不播每一步工具日志 |
| 需要补充 | 完整问题与必要选项，保持可见 | 开启自动朗读时优先读问题 |
| 返回结果 | 首段结论，展开完整正文与来源 | 短回复读全文；长回复先读结论，允许继续朗读 |
| 执行失败 | 原因和可执行的下一步 | 简短读失败原因；不要只发提示音 |
| 外部应用派单 | 已向 WorkBuddy 提交，尚未获得执行结果 | 不说“任务已完成” |

默认自动出现不激活 PocketDesk，不切应用、不挪鼠标、不改手机当前接收者；长文不自动消失，用户关闭后仍可查看历史。需要用户回应的内容持续显示，但不循环播报。

控制保留“展开/收起、朗读/停止、自动朗读开关”。停止朗读只停止声音，不能标为停止任务。默认先文字，用户开启后才自动播放；锁屏时隐藏敏感正文并停止朗读，解锁不自动补播。

追问示例：手机说“帮我整理这个页面” → 电脑显示“要简短摘要还是行动清单？” → 手机继续说“行动清单” → 同一任务接续 → 电脑显示结果，按设置朗读。无需回手机查看问题。

## 6. 最小实现边界

建议的数据流：

```text
手机输入/听写 → 现有 TaskService → AgentRunner → TaskStore
                                                 │ 已确认状态/消息
                                                 ▼
                                        电脑反馈协调层
                                         ├─ 原生文字窗
                                         └─ 系统 TTS
```

- 复用 TaskStore；持久化成功后向主线程发布不可变快照，订阅回调不得在存储锁内执行。展示错误与存储失败要显式处理，不能沿用吞错路径宣称成功。
- 反馈协调层只筛选可展示内容与调度输出，不执行工具、不改任务状态。tool 消息和模型内部推理不直接展示或朗读。
- 状态更新按 taskId/revision 去重；朗读按 taskId/messageId/内容版本去重。重启恢复历史只显示，不自动补播；手动重读不重跑任务。
- 回复优先读取已持久化 result/error，保留页面漂移等告警，不能只取原始模型内容导致漏掉限定条件。
- 朗读维护单一串行队列和播放代际；停止后清空缓冲并拒绝迟到音频。新一轮已提交时中断旧朗读，文本内容仍保留。
- 首版不声称“你一开口它就停”：手机系统听写未向网页提供可靠的语音起始事件。先支持显式停止与提交新消息时中断；可靠的自然插话需要另做音频采集/VAD。
- 朗读前清理 Markdown 标记，不默认念代码块、长 URL 和工具日志。保留否定词、金额、日期和失败限定语；首版优先约束原始回答先给短结论，避免额外模型摘要改变含义。
- 原生 AppKit 窗口与 TTS 在 Mac 进程内消费事实，无需给控制/画面 WebSocket 添加音频包，也不依赖手机页面保持前台。
- 现有状态枚举先复用；外部派单的投递证据用于覆写显示文案，不能把小精灵本轮结束等同于外部任务完成。

建议按职责新增小型反馈协调层、原生面板、语音服务文件，并在 main 装配；暂不搭建多供应商插件平台。实际新增文件时补 L3、Sources/CLAUDE.md 和 L1 地图。

## 7. 分阶段交付与验收

### P0：电脑文字闭环

交付接收、执行、追问、结果、失败展示和同一任务接续。使用已存在的完整回复，不模拟逐字生成。

验收：手机提交后无需查看手机即可知道进度与问题；反馈窗自动出现期间，目标应用 PID 与输入框焦点保持不变；短回复、长文、失败、追问均可读；重复事件不重复插入；手机提交成功后即使页面进入后台，Mac 仍展示最终结果；重启能查看记录但不会宣称旧任务刚完成。

### P1：系统 TTS

交付可用中文音色选择、试听、手动朗读、自动朗读、停止与纯文本降级。无需新增云端密钥。

验收：真实中文回复可听；停止后无残留队列续播；新提交能停旧声音；同一消息不会因刷新重播；音色缺失/音频失败不影响任务与文字；锁屏停止播报；耳机和扬声器切换行为经过实机确认。

### P2：按体验证据升级

若系统声音不满足需求，用真实中文、中英混读、数字日期、长句各类样本，对比系统音色和一个云服务候选。记录端到端首声延迟 p50/p95、失败率、停止响应、计费字符与账单口径；不拿厂商模型推理延迟冒充用户等待时间。

确需边生成边说，再让 ModelClient 支持流式文本，并按完整句/语义短句送 TTS；不能朗读未确认的工具执行成功文案。云端故障保留文字，凭证仅在 Mac，费用与 LLM 用量分开。

### 外部应用回复：单独验收

优先调查各应用官方 API、事件或完成回调，绑定真实 conversation/task/message ID。无接口时再评估指定应用的 AX/网页读取，并验证角色识别、旧消息去重、完成信号与会话切换。不把“界面几秒没变”当完成证据，不轮询截图猜一切。当前先保证投递回执准确。

## 8. 仍待验证

本次完成静态代码核对与官方资料调研，未修改或启动语音功能，也未试听。系统中文音色质量、多屏/全屏 Spaces、不抢焦点、端到端延迟与 WorkBuddy 回调能力都需要后续实测。推荐先实施 P0，再接 P1；P2 由实际体验决定。
