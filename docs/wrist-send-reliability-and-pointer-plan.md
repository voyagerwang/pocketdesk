# 翻腕发送可靠性与应用选择鼠标就位

状态：2026-09-11 方案已定，交给 WorkBuddy 按顺序实现。

## 目标

这次不调手势灵敏度，修的是翻腕发送所依赖的两条基础链路：手机 HTTPS 长期可用、每轮草稿在焦点短暂中断后可安全恢复。同时落地“手动选择应用后鼠标进入该应用窗口”，让用户随后直接使用手机触控板。

最终体验：首次完成必要授权后不再反复索要未知钥匙串密码；一次发送结束后可直接开始下一轮；普通弹窗短暂抢焦点时暂停而不误输，弹窗消失并回到原输入框后自动继续；无法证明原位置时清楚提示用户点一下输入框，不要求通过切换应用重置内部状态。

## 已确认的根因

### 1. “密钥/授权”反复出现

这不是翻腕传感器授权。HTTPS 使用的证书私钥被导入随机密码的临时钥匙串；该钥匙串可能因闲置、睡眠或 securityd 状态变化重新上锁。TLS 握手再次取私钥时会触发 macOS 钥匙串密码或私钥使用授权，而用户不知道随机密码，网络线程也可能卡在等待中。

WorkBuddy 当前正在 Sources/SecureTransport.swift 和 Sources/main.swift 做修复，工作区已有未提交实现：App 私有钥匙串、关闭自动上锁、限定访问主体、周期补解锁及服务看门狗。先完成审阅与验证，不丢弃或覆盖这些改动。必须验证它没有引入反复授权、私钥进入登录钥匙串、看门狗误杀活跃输入或多个实例争抢端口；密码文件必须是 0600，退出和陈旧文件清理必须可证实。

iOS 的“运动与方向访问”是另一项系统权限：只允许由用户手势请求一次。页面加载、恢复监听、切后台再回来都只能读取状态，不能主动再次弹权限框；已拒绝时给一次就地说明，不循环请求。安卓安全上下文不显示伪“已授权”提示。

### 2. 第二轮或弹窗后停止同步

当前正确地在焦点/绑定变化时停止草稿，避免内容落入系统弹窗或别的窗口；问题在于停止后的恢复只能依赖用户重选应用。Web/compose.js 的 `livePaused` 会阻止后续 `scheduleLive()`，而弹窗关闭、页面重新聚焦或新一轮发送后没有统一的安全重绑流程。

发送后 WorkBuddy 等 Electron 应用会重建编辑器 AX 对象，或短暂把焦点落到应用容器；系统弹窗也会临时改变前台进程/聚焦元素。旧 InputBinding 严格失效是正确行为，不能放宽到“同应用就继续写”。缺的是区分以下状态：

- `active`：绑定有效，可同步；
- `interrupted`：焦点暂时丢失，冻结队列并保留手机正文、已确认电脑前缀和原绑定身份；
- `recoverable`：原目标应用与原编辑位置重新出现，服务端核验电脑内容仍等于最后确认状态；
- `needs-user-focus`：目标应用回来了，但无法证明是原输入位置；提示“点一下电脑输入框即可继续”，不要要求切换应用；
- `committed`：上一轮封闭，新输入必须建立全新草稿与绑定，绝不继承旧编辑器对象。

## 实施顺序

### A. 先完成安全通道修复

1. 审阅并完成当前 SecureTransport 改动，优先用单一 App 私有钥匙串生命周期解决，不向登录钥匙串回退。
2. 看门狗只能在连续、独立健康探测确认公共服务线程失活后重启；提交/图片粘贴/草稿写入进行中不得重启。重启必须单实例交接，不能产生双服务。
3. 验证冷启动、运行超过原自动锁定窗口、睡眠唤醒、连续 HTTPS 握手和正常退出；观察整个过程无密码/授权弹窗。无法自动模拟的 system prompt 记为真机待验收。

### B. 建立跨弹窗的安全恢复协议

1. InputBinding 增加不可伪造的绑定身份与只读快照；保留原 PID、元素/页面范围、最后确认文本边界和失效原因。不要用“当前仍是同一个 bundle”代替原位置核验。
2. InputExecutor/LiveDraft 返回结构化状态码，例如 `focus_interrupted`、`needs_user_focus`、`context_rebound`，人类文案留在边界层。临时焦点中断不销毁已确认草稿状态，也不把失败请求标成已输入。
3. Web/compose.js 收到可恢复中断后进入冻结态：保留最新手机全文，停止自动请求风暴。监听 `visibilitychange`、窗口 `focus`、输入框重新聚焦，以及低频有界探针；任一事件仅发只读恢复请求，不直接重放正文。
4. 服务端只有在以下证据同时成立时返回可续接：控制租约仍属于当前会话；目标应用重新前台；原 AX 元素仍相同，或同一聚焦窗口/WebArea 内的新编辑器可被核验；电脑内容与最后确认文本/选区边界一致。成功后只发送最后确认版本之后的差量或按既有选区算法更新。
5. 若 WorkBuddy 发送后编辑器为空且对象重建，把它识别为上一轮 committed 后的全新编辑位置，建立新 draft/context；下一轮首字允许短暂等待编辑器出现并自动绑定。等待应有短上限，不能无休止轮询。
6. 系统弹窗打开时不得发送键盘事件。弹窗关闭后若原元素与内容可核验则自动恢复；若焦点落到应用容器，显示一条可行动提示，用户点回电脑输入框后自动恢复，不必切应用。若用户已在电脑端修改原文，保持暂停并要求核对，禁止整段重放。
7. 翻腕候选在 `interrupted`、恢复探测中、上一轮提交收尾中一律不发送。手势一次只绑定一个 draft generation；迟到候选和迟到 HTTP 回执不能提交新一轮草稿。

### C. 应用选择后鼠标就位

按 docs/app-selection-pointer-plan.md 完整实施，并与本次恢复协议共用选择代际和控制租约。只在手机手动选择应用成功后触发；鼠标已在目标窗口可见区域内则不动，否则移动到可见区域中央；不点击、不改变焦点。自动跟随、文本发送的隐式激活与恢复探针均不得带鼠标副作用。

## 测试矩阵

- 安全通道：冷启动、10 分钟持续连接、睡眠唤醒、securityd/钥匙串重新锁定场景；HTTPS、HTTP、WS 心跳均可恢复且不弹未知密码。
- 连续草稿：WorkBuddy 连续发送至少 20 轮，每轮发送后直接输入下一轮；记录首字、末字、提交各自回执，不允许漏字或重复。
- 弹窗：输入中出现应用内模态框、macOS 系统弹窗、通知/授权窗；弹窗存在时零误输，关闭并回到原输入框后自动续接。电脑正文被手改时必须保持暂停。
- 焦点对象重建：Electron/Chromium 提交后 composer 重建、切后台再回来、手机浏览器前后台切换、网络短断；不通过切应用恢复。
- 并发：翻腕触发与发送按钮同时、A/B 快切、旧请求迟到、控制权交接；每个草稿最多提交一次。
- 鼠标：执行 docs/app-selection-pointer-plan.md 中单屏、多屏、窗口内保持、用户移动取消、拖动取消和快速切换测试。

纯函数/状态机测试覆盖上述分支；Swift 构建、现有测试、前端语法与浏览器回归全部通过后再安装本机 App。真机至少覆盖用户实际 iPhone、安卓手机与 WorkBuddy；不能完成的真机项必须明确写“待验收”，不能用模拟器结论代替。
